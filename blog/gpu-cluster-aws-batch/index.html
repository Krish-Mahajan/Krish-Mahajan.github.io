Before the First Gradient: Standing Up a 160-GPU Training Cluster on AWS

How we provisioned, networked, and orchestrated 20 GPU nodes into a single distributed training job — before the first gradient ever flowed.

TL;DR
  • AWS Batch provisions nodes and injects identity — but every networking, NCCL, and coordination variable is configured by engineers in shell scripts and Dockerfiles.
  • EFA (Elastic Fabric Adapter) enables OS-bypass, RDMA-like networking that makes multi-node GPU collectives fast — but only if 15+ environment variables are set correctly.

Who is this for: ML infrastructure engineers, platform engineers provisioning GPU clusters, distributed training practitioners, and applied scientists who use multi-node training but want to understand what happens before torchrun starts.

In Part 1, I described how we streamed 20+ TB of multimodal data to 160 H100 GPUs using MosaicML Streaming — the data plane. That post assumed the cluster was already up and running. This post fills in the other half: how 20 independent GPU nodes became a single, coordinated distributed training job.

This is the infrastructure that sits beneath the loss curve. None of it is visible in training logs or W&B dashboards, but every piece must be correct before the first loss.backward() call can succeed across 160 GPUs. Getting even one environment variable wrong doesn't produce an error — it produces a hang that wastes hours of GPU time.

I'll walk through the complete cluster bring-up sequence: from hardware provisioning to the moment the first gradient flows across 20 nodes. For each step, I'll be explicit about what AWS Batch provides automatically versus what we had to build and configure ourselves.

The Hardware: What a Multi-Node GPU Cluster Actually Looks Like

The training cluster runs on AWS p5.48xlarge instances — the highest-performance GPU instance type in EC2 at the time of deployment. Each node packs:

  • 8× NVIDIA H100 SXM5 GPUs (80 GB HBM3 each, 640 GB total GPU memory per node)
  • NVSwitch fabric at 900 GB/s bidirectional bandwidth between any two GPUs on the same node
  • 192 vCPUs and 2 TB system memory
  • 8 TB local NVMe SSD (8× 1 TB drives) for high-speed scratch storage
  • 32× Elastic Fabric Adapter (EFA) network interfaces delivering 3,200 Gbps aggregate bandwidth for inter-node GPU collectives

Twenty of these nodes provide 160 H100 GPUs. The distinction between intra-node and inter-node communication is fundamental to everything that follows:

Intra-node (GPUs 0–7 on the same machine): NVSwitch provides direct GPU-to-GPU transfers at 900 GB/s. This is essentially free — no network stack involved.

Inter-node (any GPU talking to a GPU on a different machine): Traffic must traverse the EFA network. Fast (3200 Gbps), but orders of magnitude slower than NVSwitch and requires correct driver, protocol, and environment variable configuration.

The Dockerfile pre-creates a directory structure under /tmp/instance_storage/ for model downloads, Hugging Face cache, datasets, and tokenized data. At runtime, this path maps to the local NVMe drives — giving each node 8 TB of high-speed scratch space that persists only for the lifetime of the job.

Choosing an Orchestrator: AWS Batch vs. SageMaker vs. Ray

Before writing a single line of shell script, our team had to make a foundational decision: which orchestration layer manages the multi-node job lifecycle? The three realistic options on AWS are AWS Batch, SageMaker Training Jobs, and Ray Train on EC2. Each represents a different point on the control-vs-convenience spectrum.

Dimension AWS Batch SageMaker Training Ray Train (EC2)
P5 / H100 instance support ✓ Full ✗ Not available in our target region at the time ✓ Full (self-managed)
Multi-node job setup Built-in via numNodes Built-in via instanceGroups Ray cluster YAML + Ray Train API
EFA / NCCL configuration Fully manual Partially managed Fully manual
Managed rendezvous / sync barrier ✗ None Partial ✓ Ray handles it
Fault tolerance ✗ Manual re-run Basic retry ✓ Actor-level recovery
Instance cost overhead EC2 pricing SM surcharge applies EC2 pricing
Operational complexity Low — familiar to most teams Medium High if Ray is new to team

Why AWS Batch Was Chosen

⚠️ P5 Access: AWS Batch Only

p5.48xlarge instances (H100 GPUs) were available exclusively through AWS Batch in our deployment environment. SageMaker Training Jobs did not support P5 instances in the target region at the time of deployment. This single infrastructure constraint made the orchestrator decision straightforward — SageMaker was not on the table.

Ray Train is a compelling long-term option. Its actor-based coordination model handles rendezvous, synchronization barriers, and worker failure recovery natively — eliminating the bash-level primitives described in later sections of this post. However, Ray had not been adopted within the team at the time. Introducing it would have added a significant new dependency and operational surface area on top of an already complex bringup.

AWS Batch was already in the team's operational toolkit. It offers native multi-node job support with the AWS_BATCH_JOB_* environment variables that slot directly into torchrun, direct EC2 pricing with no managed overhead, and full control over every layer of the networking stack.

⚠️ The Price of Raw Control

AWS Batch gives engineers complete ownership of the cluster stack — but that ownership is total. There is no managed rendezvous, no synchronization primitive, no built-in fault tolerance. Every mechanism described in the remainder of this post — the 15+ EFA/NCCL environment variables, the nc -z TCP barrier, the 3-hour rendezvous timeout — is the direct consequence of choosing raw control over a managed abstraction.
Looking ahead: Ray on EC2

As the team and infrastructure mature, Ray Train is worth revisiting. ray.train.TorchTrainer can replace the bash-level sync barrier and rendezvous timeout tuning with actor-based coordination. The EFA/NCCL environment variable configuration remains necessary regardless of orchestrator — but everything above that layer becomes significantly simpler.

The Container Image: Building a GPU-Ready Training Environment

Every piece of software that runs on the cluster — PyTorch, CUDA, flash-attention, LLaMA-Factory, even the netcat utility we use for synchronization — is baked into a single Docker image. AWS Batch pulls and runs this image; we build, configure, and push it to AWS ECR for AWS Batch to pull.

Base Image Selection

We start from an AWS Deep Learning Container: pytorch-training:2.5.1-gpu-py311-cu124-ubuntu22.04-ec2. This matters because the DLC comes with pre-installed EFA drivers, NCCL, cuDNN, and a PyTorch build compiled against them. Starting from a generic Ubuntu image would mean compiling these from source — a multi-hour build with easy-to-miss version incompatibilities.

Layer-by-Layer Build

# 1. Base: AWS DLC with PyTorch 2.5.1 + CUDA 12.4 + EFA drivers
FROM 763104351884.dkr.ecr...amazonaws.com/pytorch-training:2.5.1-gpu-py311-cu124-ubuntu22.04-ec2

# 2. Python dependencies first (cache-friendly ordering)
COPY ./LLaMA-Factory/requirements.txt ./LLaMA-Factory/requirements.txt
RUN  python3 -m pip install --no-cache-dir -r ./LLaMA-Factory/requirements.txt

# 3. Flash-attention compiled from source for target hardware
ENV  FLASH_ATTENTION_FORCE_BUILD=TRUE
RUN  python3 -m pip install --no-cache-dir flash-attn --no-build-isolation

# 4. System deps — each serves a specific infra purpose
RUN  apt-get install -y netcat-openbsd pigz rsync
#    netcat: TCP probe for the sync barrier (Section 7)
#    pigz:   parallel gzip for model tarballs

# 5. LLaMA-Factory in editable mode
RUN  cd ./LLaMA-Factory && pip install -e ".[metrics]"

# 6. AWS credential config baked into image
ENV  AWS_CONFIG_FILE=/usr/local/bin/aws-config.txt

Two decisions deserve emphasis. First, flash-attn is compiled from source (FLASH_ATTENTION_FORCE_BUILD=TRUE) rather than installed from a wheel. Pre-built wheels may not match the exact CUDA toolkit and GPU architecture on the target instances. Second, the image is built on an EC2 instance, not locally — the flash-attention compilation requires a CUDA-capable build environment, and the final image is too large for most developer machines.

EFA: What It Is and Why It Matters for Multi-Node Training

Elastic Fabric Adapter (EFA) is AWS's OS-bypass networking interface. Unlike standard VPC networking where every packet traverses the kernel's TCP/IP stack, EFA allows applications to talk directly to the network hardware — similar to InfiniBand RDMA in on-premise HPC clusters. For distributed GPU training, this is the difference between tolerable inter-node communication and a system that spends more time waiting on the network than computing gradients.

AWS Batch attaches EFA interfaces to your nodes if the compute environment is configured for it — but we must tell NCCL and libfabric to actually use them. None of the following variables are set automatically. Without them, NCCL falls back to TCP sockets over the standard ENI — orders of magnitude slower.

# All of these are set by us in run_training_pipeline.sh
# AWS Batch provides NONE of them.

# Tell libfabric to use the EFA provider (not TCP sockets)
export FI_PROVIDER="efa"

# Enable RDMA for direct GPU-to-GPU transfers across nodes
export FI_EFA_USE_DEVICE_RDMA=1

# Disable GDRCopy — prevents init errors where it's unsupported
export FI_EFA_GDR_READ_ENABLE=0

# Required for multi-worker DataLoaders that fork processes
export FI_EFA_FORK_SAFE=1
export RDMAV_FORK_SAFE=1

# Restrict intra-node P2P to NVLink (fast), inter-node goes via EFA
export NCCL_P2P_LEVEL="NVL"

# LL128 protocol — optimal for P5 instances with EFA
export NCCL_PROTO=LL128

# Bootstrap NIC selection — must match actual interface names
export NCCL_SOCKET_IFNAME="ens,eth0"
export GLOO_SOCKET_IFNAME="ens,eth0"

The most important variable is FI_PROVIDER=efa. If this isn't set, the job will silently fall back to TCP — training will work, but collective operations will be 10× slower. Machine Learning Infra engineers actually set this to fail-fast: if the EFA provider can't be loaded, libfabric will error out rather than silently degrading to sockets.

NCCL_P2P_LEVEL=NVL tells NCCL to restrict peer-to-peer direct transfers to NVLink-connected GPUs (i.e., same node only). Cross-node transfers are routed through EFA. This prevents NCCL from attempting PCIe-based P2P across nodes, which would be catastrophically slow.

NCCL_PROTO=LL128 selects the Low-Latency 128-byte protocol, which is optimized for the EFA network characteristics on P5 instances. The alternative (Simple) can be faster on InfiniBand but performs worse on EFA's packet structure.

Node Discovery: How Nodes Find Each Other

Before torchrun can assign ranks, nodes must know each other's existence and agree on a master address. This is the "service discovery" problem for distributed training — and it's where the AWS Batch ↔ your-code handoff is most explicit.

What AWS Batch Gives You

AWS Batch multi-node jobs automatically inject four environment variables into every container:

# Injected by AWS Batch — you do NOT set these
AWS_BATCH_JOB_NUM_NODES=20
AWS_BATCH_JOB_NODE_INDEX=0       # unique per node, 0-based
AWS_BATCH_JOB_MAIN_NODE_INDEX=0
AWS_BATCH_JOB_MAIN_NODE_PRIVATE_IPV4_ADDRESS=10.0.1.42

What You Do With Them

AWS Batch tells each node who is the main node and provides its IP. But PyTorch doesn't read AWS Batch environment variables — it expects MASTER_ADDR and MASTER_PORT. This translation is your responsibility:

# Our code in run_training_pipeline.sh — translates Batch vars to PyTorch vars
if [ "${AWS_BATCH_JOB_NODE_INDEX}" == "${AWS_BATCH_JOB_MAIN_NODE_INDEX}" ]; then
    # Main node resolves its own IP
    export MASTER_ADDR=$(hostname -i)
else
    # Workers read the main node's IP from Batch
    export MASTER_ADDR=${AWS_BATCH_JOB_MAIN_NODE_PRIVATE_IPV4_ADDRESS}
fi
export MASTER_PORT=29500

Rank Assignment and the Distributed Topology

Rank assignment is the bridge between "N independent machines" and "one logical distributed job." It determines which GPU processes which shard of data and which slice of the model. Here's how the three-layer rank taxonomy works:

Rank Type Scope Range (20 nodes × 8 GPUs) Set By
NODE_RANK Which machine 0–19 Our team
LOCAL_RANK Which GPU on that machine 0–7 torchrun
RANK (global) Unique ID across all GPUs 0–159 torchrun
WORLD_SIZE Total GPU count 160 torchrun

The key insight: torchrun handles local rank assignment and calculates global ranks automatically — but you must tell it the global topology by translating AWS Batch's environment variables:

# We set these by reading AWS Batch env vars
export FORCE_TORCHRUN=1
export NNODES=${AWS_BATCH_JOB_NUM_NODES}         # ← from Batch
export NODE_RANK=${AWS_BATCH_JOB_NODE_INDEX}      # ← from Batch
export MASTER_ADDR=...                            # ← resolved by us
export MASTER_PORT=29500                          # ← chosen by us

# torchrun then AUTOMATICALLY sets per-process:
# LOCAL_RANK, RANK (global), WORLD_SIZE

We also configure generous rendezvous timeouts. With 20 nodes that may take varying amounts of time to download models and prepare data, the default timeouts are too aggressive:

# AWS Batch does NOT set these — without them, large jobs timeout
export RDZV_CONF="last_call_timeout=60,join_timeout=10800,close_timeout=10800,timeout=10800"

The 3-hour (10800s) join timeout may seem excessive, but it accounts for the worst case: a node that downloads a large model from S3 while others have already finished. Without this, torchrun will kill the rendezvous and you'll see timeout errors that look like networking problems but are actually just sequencing problems. In practice, model downloads on P5 instances with S3 complete in minutes, not hours — so this timeout is a safety margin against cold-start variance, not a license for nodes to silently stall for 3 hours while burning GPU-time on the rest of the cluster.

NCCL Initialization: The Handshake That Makes It All Work

NCCL initialization is the moment when the cluster transitions from "N processes that know about each other" to "N processes that can do collective communication." It's also the most common failure point. AWS Batch has no knowledge of NCCL and provides zero configuration for it — every variable here is set by us.

The initialization happens in two phases:

Phase 1: Gloo Rendezvous (TCP, lightweight) — All processes connect to the master node's MASTER_ADDR:MASTER_PORT using the Gloo backend. This is a simple TCP handshake that establishes the process group topology. GLOO_SOCKET_IFNAME=ens,eth0 tells Gloo which NIC to use.

Phase 2: NCCL Communicator Creation (EFA, GPU-aware) — NCCL creates its own communication channels using the EFA provider, probing the GPU topology, selecting optimal ring/tree algorithms, and testing bandwidth between all pairs of nodes.

The environment variables that govern this phase are critical:

# Fail fast on async NCCL errors instead of hanging
export TORCH_NCCL_ASYNC_ERROR_HANDLING=1

# Enable PXN for multi-NIC topologies on P5
export NCCL_PXN_DISABLE=0

# CRITICAL: Allow EFA to pin sufficient memory for RDMA buffers
ulimit -l unlimited

# Mitigate CUDA OOM from memory fragmentation
export PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True

The ulimit -l unlimited call is frequently missed. EFA needs to pin large memory regions for RDMA buffers. If the memlock limit is too low, you'll see cryptic ib_mr_reg_lsmr errors during NCCL init. This is set in entrypoint script, not the Dockerfile, because ulimit must be applied at runtime.

The Synchronization Barrier: Making Sure Everyone's Ready

In theory, AWS Batch launches all 20 containers at the same time. In practice, startup times vary by minutes — some nodes are still downloading the base model from S3 when others are ready to train. Without a barrier, fast nodes will start torchrun, which begins the rendezvous countdown. If slow nodes don't join before the timeout, the entire job fails with errors that look like networking problems.

AWS Batch provides no synchronization primitive — no barrier, no readiness signal, no health check. We built our own using the simplest possible tool: a netcat TCP probe.

# From run_training_pipeline.sh
# Workers wait until the main node's torchrun port is reachable
if [ "${AWS_BATCH_JOB_NODE_INDEX}" != "${AWS_BATCH_JOB_MAIN_NODE_INDEX}" ]; then
    echo "WORKER NODE (Rank ${NODE_RANK}). Waiting for main node..."
    while ! nc -z -w 10 ${MASTER_ADDR} ${MASTER_PORT}; do
        echo "Main node not yet reachable. Retrying in 15 seconds..."
        sleep 15
    done
    echo "Main node is ready. Proceeding to training."
fi

This is six lines of bash, but it solved what was operationally the most difficult problem. The barrier works because torchrun on the main node opens MASTER_PORT when it's ready for rendezvous. Workers probe that port in a loop. Once reachable, they know the main node is ready and proceed to launch their own torchrun process.

Note that netcat-openbsd is a deliberate dependency in the Dockerfile. It's the simplest tool that solves the problem — no Python, no library, no daemon. Alternatives include S3-based barriers (each node writes a sentinel file, leader polls for all), Redis, or etcd. For this scale (20 nodes), the TCP probe is sufficient and has zero infrastructure dependencies.

What Can Go Wrong: A Field Guide to Cluster Debugging

The most important thing to know about GPU cluster debugging: failures almost always present as hangs, not errors. The job will sit there consuming GPU-hours while 20 nodes silently wait for a TCP connection, an NCCL communicator, or a rendezvous response that will never come. The table below documents every failure we encountered, what it looked like, and how to fix it.

Failure Symptom Fix Owner
Wrong NCCL_SOCKET_IFNAME NCCL tries wrong NIC, hangs Check ip addr on instances Script
ulimit -l too low ib_mr_reg_lsmr error ulimit -l unlimited Script
Port conflict on 29500 torchrun fails to bind Clean zombie processes or use different port Script
FI_PROVIDER not efa Falls back to TCP, 10× slower export FI_PROVIDER=efa Script
Mismatched NNODES Rendezvous hangs or errors Verify AWS_BATCH_JOB_NUM_NODES Script
GDRCopy errors NCCL init fails with gdrcopy trace FI_EFA_GDR_READ_ENABLE=0 Script
Memory fragmentation CUDA OOM despite free memory PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True Script
Missing netcat Sync barrier errors or skipped Add netcat-openbsd to Dockerfile Dockerfile
The Golden Debugging Sequence

When your distributed training job hangs, check these five things in order:
  • 1. Interface names — Run ip addr on a node. Does NCCL_SOCKET_IFNAME match the actual interface?
  • 2. NCCL_DEBUG=INFO — Set this and re-run. The verbose logs will show exactly where NCCL is stuck (NIC selection? topology probing? communicator creation?)
  • 3. ulimit -l — Run ulimit -l inside the container. If it's not unlimited, EFA can't pin RDMA buffers.
  • 4. FI_PROVIDER — Echo $FI_PROVIDER. If it's empty or not efa, NCCL isn't using EFA at all.

The First Successful Step: Putting It All Together

With all the infrastructure in place, here's what happens when run_training_pipeline.sh executes end-to-end:

1
AWS Batch launches 20 containers

Each gets EFA interfaces, IAM credentials, and identity env vars (AWS_BATCH_JOB_*). The container image is pulled from ECR.

2
Our script configures 20+ environment variables

EFA/NCCL settings, master address resolution, rank assignment, rendezvous timeouts, ulimit adjustments. None of this comes from Batch.

3
Each node downloads the base model

Extracted to local NVMe under /tmp/instance_storage/. Download times vary across nodes.

4
The synchronization barrier fires

Worker nodes loop on nc -z until the main node's torchrun port is reachable. Fast nodes wait; slow nodes catch up.

5
llamafactory-cli train launches

FORCE_TORCHRUN=1 tells LLaMA-Factory to invoke torchrun internally. Gloo rendezvous completes, NCCL communicators are created, and 160 processes form a single distributed process group.

6
The first gradient flows

Forward pass, loss computation, loss.backward(), AllReduce across 160 GPUs via EFA. MDS starts streaming tokenized data from S3 as described in Part 1. The loss curve begins.

The Final torchrun Command

Every variable set in the previous sections converges into a single call inside LLaMA-Factory's cli.py. When FORCE_TORCHRUN=1 is set, llamafactory-cli train skips its single-GPU path and constructs a torchrun command from the environment: 

# Inside llamafactory/cli.py — runs when FORCE_TORCHRUN=1
torchrun \
  --nnodes     ${NNODES}            # ← from AWS_BATCH_JOB_NUM_NODES
  --nproc_per_node ${NPROC_PER_NODE}  # ← 8 (one per H100)
  --rdzv_backend c10d
  --rdzv_endpoint ${MASTER_ADDR}:${MASTER_PORT}
  --rdzv_conf  '${RDZV_CONF}'        # ← 3hr join/close timeouts
  --node_rank  ${NODE_RANK}           # ← from AWS_BATCH_JOB_NODE_INDEX
  launcher.py  [training args]
One subtlety worth noting: cli.py also injects a final set of EFA/libfabric variables (FI_PROVIDER=efa, FI_EFA_RX_CQ_SIZE=8192) directly into the torchrun subprocess environment, on top of what the shell script already exported. This double-setting is intentional — it guarantees EFA is active even if the outer env is somehow dropped during the subprocess fork under /bin/bash -lc.

Key Takeaways

Building a multi-node GPU training cluster is an exercise in managing invisible dependencies. The hardware, networking, and orchestration must all be correct before a single line of PyTorch code executes — and most misconfiguration manifests as silence, not errors.

The single most important insight from this work: the gap between "AWS gives you GPUs" and "training actually starts" is larger than most people expect. Here's the ownership breakdown:

AWS Batch Handles Our Configuration
✓ Instance provisioning & lifecycle Container image (base, CUDA, flash-attn, LLaMA-Factory, system deps)
✓ EFA interface attachment Container image (base, CUDA, flash-attn, LLaMA-Factory, system deps)
✓ Container image pull from ECR All EFA/NCCL env vars (FI_PROVIDER, NCCL_PROTO, etc.)
✓ Node identity env vars (AWS_BATCH_JOB_*) Master address resolution from Batch env vars
✓ IAM credential injection Synchronization barrier (nc -z probe loop)
ulimit -l unlimited, rendezvous timeouts
PYTORCH_CUDA_ALLOC_CONF, torchrun log level

With the cluster operational, the data plane takes over — MDS starts streaming tokenized shards from S3, each GPU processes its deterministic subset, and the loss curve begins its descent. That machinery is described in Part 1. Together, the two posts cover the full stack: from hardware provisioning to the start of the learning phase.
